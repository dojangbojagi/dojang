# Hero 3D (right side) — rebuild and maintenance handoff (4 Oct 2026)

Written for the engineer or agent who has to **recreate, tune or extend the 3D planet on the right side of the landing hero**, exactly as in the reference screenshot (stage 0, 1440×900: tilted glassy planet with lattice, vault core, blue and amber ring systems, four mini-planets, star-field backdrop).
Scope: only the right-side visual. Hero copy, floating nav, CA pill and the rest of the page are in `HANDOFF_2026-10-04.md`.

**Can it be rebuilt exactly like the reference? Yes.** It is not a model or a texture: it is ~1,700 lines of Canvas 2D that does its own 3D math. Everything needed is in this document: the math, the draw order, every constant table, the camera system and a milestone plan with acceptance checks. The working implementation is `components/landing/HeroVisual.tsx`; if it is ever lost, restore it from git (§13) instead of re-deriving it.

## 2. Technology choice (and when to change it)

**Canvas 2D with hand-written projection**, one `<canvas>`, one `requestAnimationFrame` loop, no dependency.

| Option | Verdict for this look |
|---|---|
| **Canvas 2D (current)** | Crisp hairlines at any zoom, exact control of front/back ring halves, additive glows, tiny bundle, 19–30 % CPU in the headless comparison. Chosen |
| SVG | The previous version: ~1,000 nodes mutated per frame + ~100 CSS animations; heavy. Rejected |
| CSS 3D | Cannot do lattice shading, ring wrapping or glows |
| three.js / R3F | Right call only if you need textured planets, real lighting or post-processing. Cost: +150 KB gz, a rebuild of every layer (LineSegments for the lattice, ring geometry split by depth, sprites for glows), and thin 0.8 px lines need a custom shader to match this crispness |

Measured when the Canvas version replaced SVG (headless Chrome, same frame rate, two rounds): CPU 65–79 % → 19–30 %; worst frame during stage travel 185 ms → ~30 ms. Treat as relative numbers, not device numbers.

## 4. Coordinate systems and math

### 4.1 Planet space
Units where the planet radius is `R = 345`. Origin = planet centre. X right, Y up, Z toward the viewer. The planet's own state is two angles in degrees: `currentX` (tilt, starts at 17) and `currentY` (spin, accumulates).

### 4.2 View transform
```ts
const z  = z0 * cam.m;                                   // screen px per planet unit
const ax = cam.au * W + clamp(ptrX * 5, -6, 6);          // where the focus point lands on screen
const ay = cam.av * H + clamp(ptrY * 4, -5, 5);
const cx = ax - z * cam.fx,  cy = ay - z * cam.fy;       // planet centre on screen
ctx.translate(cx, cy); ctx.rotate(ROLL /* -14° */); ctx.scale(z, z);   // everything planet-related is drawn in planet units
```
Base fit: `z0 = min(0.78·H, 0.92·0.58·W) / (2R)` on desktop; `min(0.9·W, 0.52·H) / (2R)` below 1024 px.

### 4.3 Projecting a point (tilt about X, spin about Y)
```ts
// (X, Y, Z) in planet space, after spin has been applied to its longitude
const x = X;
const y = -(Y * cosT - Z * sinT);       // screen y grows downward, hence the minus
const z =   Y * sinT + Z * cosT;        // depth: larger = closer to the viewer
```
Latitude ring φ (radius `rr = R cos φ`, `Y = R sin φ`): `X = rr·sin θ`, `Z = rr·cos θ`, θ = 0…2π (72 segments).
Meridian m: θm = m·20° + spin; for φ from −90° to 90° (36 steps): `rc = R cos φ`, `X = rc·sin θm`, `Z = rc·cos θm`, `Y = R sin φ`.
Surface star (lat, lon): θ = lon + spin, `X = R cos lat sin θ`, `Y = R sin lat`, `Z = R cos lat cos θ`.

### 4.4 Depth-shaded lattice (the "far faint → near bright" look)
Segments are bucketed by depth so each bucket is one `beginPath`/`stroke` (1,440 segments per frame collapse into at most 16 strokes: 4 depth buckets × latitudes/equator, for each of the two passes):
```ts
const NB = 8;
const bucketOf = (z) => clamp(Math.floor((z / R * 0.5 + 0.5) * NB), 0, NB - 1);
const BUCKET_ALPHA = Array.from({ length: NB }, (_, b) => 0.04 + 0.6 * Math.pow((b + 0.5) / NB, 1.7));
```
Buckets 0–3 are painted **before** the core, buckets 4–7 **after**; latitudes use 0.8 px lines, the equator is 1.2 px at ×1.5 alpha.
Tables: latitudes `[-75…75 step 15]` (11 incl. equator) × 72 segments, 18 meridians × 36 segments.

### 4.5 Rings with a correct front/back split (the key trick)
A ring in the equatorial plane projects to an ellipse `rx = r`, `ry = r·|sin tilt|`. Draw it as **two half-ellipses**: the back half before the planet body, the front half after.
```ts
function ringHalf(ctx, ring, front, sinT, k, inv, t) {
  const ry = Math.max(0.01, Math.abs(ring.r * sinT));
  const a0 = (sinT >= 0 ? 0 : Math.PI) + (front ? 0 : Math.PI);     // sign of the tilt flips which half is nearer
  ctx.beginPath();
  ctx.ellipse(0, 0, ring.r, ry, 0, a0 - SEAM, a0 + Math.PI + SEAM); // SEAM = 0.004 rad: halves overlap a hair
  …stroke with rgba(ring.rgb, ring.a * k)
}
```
Dashed rings: the dash pattern is **fitted to the full perimeter** (`per = π(3(a+b) − √((3a+b)(a+3b)))`, `fit = per / (round(per/patLen) · patLen)`) and the back half is phase-shifted by half the perimeter, so the pattern runs unbroken around the whole ring. `lineDashOffset = flow·t (+ per/2 for the back half)` animates the flow. `band: true` rings are wide, translucent strokes (the soft glow band).
`k` scales alpha with stage emphasis: `fk = clamp(fixedOp/0.72, 0.4, 1.45)` for the blue system, `lk` for the amber one.

### 4.6 Moons
On the ring plane: `a = t/period·2π + phase`, `x = r·cos a`, `y = r·|sinT|·sin a`. A moon is in front when `sin a` has the same sign as `sinT`. Each is a white dot plus an additive glow; back-side ones are dimmer (glow ×0.6, dot ×0.7).

### 4.7 Vault core
Drawn inside `ctx.rotate(-ROLL)` so its labels stay upright. Two cubes (outer `S = 70`, inner `S = 36`), rotated by `Rx(currentX)` then `Ry(currentY)`, 12 edges each + 8 struts between them; edge alpha and width interpolate with depth (`depth(z) = smooth((z+40)/80)`). Nucleus: dashed ring r12, white glow r26, amber glow r30 (alpha 0.25 → 0.5 with `engineVis`), white dot r5.5. Two faint dashed orbit ellipses (115 × 48 px rotated +35°, and 92 × 35 px rotated −40°). At stage 3 two lasers fire left (blue, `PT (PRINCIPAL)`) and right (amber, `YT (YIELD)`). Label under the core: `labels.core`.

### 4.8 Mini-planets are screen-aligned on purpose
```ts
pin.x = ax + z * (PIN_POS[i][0] - cam.fx);
pin.y = ay + z * (PIN_POS[i][1] - cam.fy);     // no tilt, spin or roll applied
```
So their art is always upright and readable while the planet turns. Body radius is 26 pin-units (scaled by `z`), plus aura, rim light (arc 160.8°→289.2°), orbit hint, badge (rounded rect at +32, −16, width 132–136, height 30).

### 4.9 Gradients (built once per resize, in unit space)
Drawn with `ctx.scale(R, R)` so one gradient serves every size:
- `body`: radial centred at (−0.34, −0.4), stops `rgba(52,86,138,.6) → (18,34,58,.64)@.32 → (6,12,22,.85)@.68 → (2,4,8,.95)` (radius 1.08).
- `atmo[key]`: radial 0.94 → 1.26 R, alpha `0 → .32@.2 → .08@.55 → 0`, colour per limb tint.
- `rim[key]`: linear gradient along the (−.78,−.78)→(.78,.78) diagonal, `white .95 → (235,242,255) .5@.32 → tint@.62 → tint@1`.
- `haloIce` / `haloAmber`: radial 0.5 → 2.4 R behind everything.
- Star sprite: 64×64 canvas radial `white .9 → .28@.3 → 0`, stamped with `drawImage` (much cheaper than a gradient per star).
- Pin bodies: four radial gradients (ice, amber, neutral, mint) offset to the upper-left.

## 6. Camera and stages

A keyframe is `{ m, fx, fy, au, av }`: zoom multiplier, the planet-space point to look at, and the screen fraction where that point lands. Because frames are screen fractions the framing holds on any viewport shape.

```ts

  { m: 1.0,  fx:    0, fy:    0, au: 0.68, av: 0.50 }, // 0 overview (planet right of the copy)

  { m: 1.4,  fx:  260, fy: -130, au: 0.84, av: 0.42 }, // 2 trading — membrane, upper right
  { m: 1.5,  fx:    0, fy:    0, au: 0.72, av: 0.56 }, // 3 split   — core laser
  { m: 1.62, fx:  200, fy:  240, au: 0.80, av: 0.66 }, // 4 market  — gyroscope, lower right
];
const CAM_COMPACT = [ // < 1024 px: planet centred, copy overlays it at 35–50 % opacity
  { m: 1.0, fx: 0, fy: 0, au: 0.5, av: 0.5 }, { m: 1.4, fx: -100, fy: 240, au: 0.5, av: 0.62 },
  { m: 1.4, fx: 260, fy: -130, au: 0.5, av: 0.4 }, { m: 1.3, fx: 0, fy: 0, au: 0.5, av: 0.5 },
  { m: 1.4, fx: 200, fy: 240, au: 0.5, av: 0.62 },
];
const PIN_POS = [[-100, 240], [260, -130], [0, -190], [200, 240]];   // planet-space positions of the four mini-planets
```

Between keyframes (desktop, scroll-driven):
```ts
function sampleCamera(frames, pos) {
  const p = clamp(pos, 0, frames.length - 1), i = Math.min(frames.length - 2, Math.floor(p));
  const k = smootherstep(p - i);                // rests on every keyframe, no overshoot
  …each field = lerp(frames[i][f], frames[i + 1][f], k)
}
```
The live camera chases that target with a **critically damped spring**, identical at 60 and 120 Hz:
```ts
const CAMERA_SMOOTH_TIME = 0.5;
function smoothDamp(cur, target, vel, smoothTime, dt) {
  const omega = 2 / smoothTime, x = omega * dt;
  const e = 1 / (1 + x + 0.48 * x * x + 0.235 * x * x * x);
  const change = cur - target, temp = (vel + omega * change) * dt;
  return [target + (change + temp) * e, (vel - omega * temp) * e];     // [position, velocity]
}
```
(`smootherstep(x) = x³(x(6x−15)+10)`.) Under reduced motion the camera snaps to its goal.

## 7. Simulation state, easing and what each stage emphasises

State (`createSim()`): orientation (`currentX/Y`, `targetX/Y`, `velocityX/Y`, hover tilt), pointer (`ptrX/Y` for parallax), camera (`cam`, `camV`), eased emphasis (`fixedOp`, `longOp`, `iceBack`, `amberBack`, `limb{white,ice,amber,mint}`, `engineVis`, `vaultVis`, `pinAct[4]`, `pinVis[4]`, `pinHover[4]`), `stage`, drag bookkeeping.
Every emphasis value is eased toward its goal with `decay(6, dt) = 1 − e^(−6dt)` (hover uses 10), so **nothing ever pops**.

`emphasisGoals(s)`:

| Stage | Meaning | fixedOp | longOp | iceBack | amberBack | limb (planet's own light) | engineVis | vaultVis | active pin |
|---|---|---|---|---|---|---|---|---|---|
| 0 | overview | 0.72 (+ pointer bias) | 0.72 (+ pointer bias) | 0.55 | 0.7 | **white** | 0 | 0 | none (all 4 visible) |
| 1 | Fixed Yield | 1 | 0.35 | 1 | 0 | **ice** | 0 | 0 | 0 |
| 2 | Trading Yield | 0.35 | 1 | 0.15 | 1 | **amber** | 0 | 0 | 1 |
| 3 | How it works | 0.72 | 0.72 | 0.55 | 0.7 | **white** | 1 | 0 | 2 |
| 4 | Markets | 0.72 | 0.72 | 0.55 | 0.7 | **mint** | 0 | 1 | 3 |

Non-active pins fade to 0.25 visibility on stages 1–4 (all 1 on stage 0). Pointer bias: moving the mouse left strengthens the blue system, right the amber one (up to +0.28).

**Limb tint system.** Four pre-built gradients per element (`atmo[key]`, `rim[key]`), cross-faded by the four eased weights, so changing stage is a smooth colour blend, not a swap.
```ts
const LIMB_TINT = {
  white: { near: "169,200,238", far: "120,170,235", rimNear: .12, rimFar: .05 },   // the pale, slightly cool "white" of the overview
  ice:   { near: ICE,   far: ICE,   rimNear: .2, rimFar: .09 },
  amber: { near: AMBER, far: AMBER, rimNear: .2, rimFar: .09 },
  mint:  { near: MINT,  far: MINT,  rimNear: .2, rimFar: .09 },
};
```
`limbWeights(s)` creates the weights lazily because Fast Refresh keeps the old `sRef` object alive across edits; without it a field added later would throw inside the frame loop and freeze the planet until a full reload. Do the same for any field you add to `createSim()`.

Rest-state loop (`step(dt)`): auto-spin `SPIN_DEG_PER_S = 2.4`; inertia `keep = exp(−5·dt)`; orientation chases its target with `decay(4.5)` (`decay(18)` while dragging); hover tilt `decay(6)`; tilt clamped to −45…50°.

## 8. Interaction

| Input | Behaviour |
|---|---|
| Pointer move (mouse) | `hoverTiltX = ny·3.8°`, `hoverTiltY = nx·4.6°`; `ptrX/Y` parallax (stars shift, focus point nudges ≤6 px); cursor `grab`, `pointer` over a pin |

## 9. Performance, quality and accessibility

- **One loop**, one canvas, no per-frame DOM work. `rgba()` strings are memoised (alpha quantised to 1 %) so the loop does not allocate.
- **Pixel budget:** `dpr = max(1, min(min(devicePixelRatio, 2)·quality, √(5.2M / (W·H))))`. **Adaptive quality:** after 24 slow frames (> 26 ms each; a good frame cancels one), `quality −= 0.25` (floor 0.5) and the canvas is resized. Only ever lowered.
- **Pauses** when scrolled off-screen (`IntersectionObserver`) or the tab is hidden; resumes on return.
- **Reduced motion:** no spin, `t = 0`, camera snaps, and the loop **sleeps** once `settled()` (it repaints only when something is still changing, or on scroll/resize/label change).
- **NaN guard:** if any simulation number goes non-finite, the sim resets instead of freezing.
- **Text on canvas** (labels, HUD) uses the Geist Mono face; the loop repaints after `document.fonts.load('600 10px "Geist Mono"')`. Letter-spacing uses `ctx.letterSpacing` when available, otherwise per-glyph measured placement.
- **Accessibility:** the canvas is `aria-hidden`; the accessible control for stages is the hero's tablist and prev/next buttons. Mini-planet taps are pointer-only by design (keyboard users use the tabs). The reset button is only focusable after a drag.

### 10.4 Surface stars (`heroStars.ts`, 96 nodes) — exact generator

for (let i = 0; i < 96; i++) {

  lon   = (i * 137.508) % 360;                                  // golden angle
  r     = i % 24 === 0 ? 2.4 : i % 3 === 0 ? 1.8 : 1.3;

## 13. Pitfalls, restore points and verification

**Pitfalls (all hit at least once)**
1. **Fast Refresh keeps `sRef`**: new `createSim()` fields must be created lazily (`limbWeights` pattern) or the loop throws and freezes. After editing `HeroVisual.tsx`, hard-reload the tab; an open tab can keep painting the previous effect closure.
2. **Gradients belong to the context** and are rebuilt in `resize()`; do not cache them across canvas resizes.
3. **Pointer capture only after the drag threshold**, otherwise taps on pins never fire.
4. **Keep the core in un-rolled space** (`rotate(-ROLL)`), otherwise labels tilt with the planet.
5. **Tilt sign:** the ring half formula (`a0`) and the moon front test both depend on `sign(sinT)`; test with a negative tilt (drag up).
6. **The copy column may overlap the canvas:** that is why the scrims exist and why orbit dots are lifted behind it. Do not "fix" legibility inside the scene.
7. **Mobile / <1024 px:** the whole visual is dimmed by its wrapper (`opacity-35 sm:opacity-50`) and centred (`CAM_COMPACT`); verify copy contrast if you brighten anything.
8. **Stages and copy are coupled by index** (§3); adding a stage means a camera frame in both tables, a `PIN_POS` entry, emphasis goals, a pin style and a stage in `heroStages.ts`.
9. **Browser support:** nothing exotic (Canvas 2D, `ellipse`, `setLineDash`, `ResizeObserver`, `IntersectionObserver`, `matchMedia`).

**Restore points** (`components/landing/HeroVisual.tsx`). Up to `dd5d1b4` (2 Oct) the scene was the old SVG version (`c59cd57` added its scroll camera). The **Canvas 2D rewrite landed in `f15165c`** (3 Oct, 1,569 lines); then `a3ceb54` backdrop and distant orbits, `5b60cb7` market-driven labels, `c0eebd1` vivid palette, `9639b00` per-stage limb light, `f72e1e8` Fast-Refresh guard (`limbWeights`), `cf18e1c` current copy (1,684 lines). The git root is above this folder, so use `git show <hash>:./components/landing/HeroVisual.tsx` (note the `./`).

5. Enable "Reduce motion": nothing spins, the camera snaps, CPU drops to idle.
